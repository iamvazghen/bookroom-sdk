# Contributing to Bookroom

Thanks for helping. This document covers how to get set up, what a good pull
request looks like, and the one rule that matters most here.

## The one rule

**Never commit a credential or copyrighted book content.**

- `.env` is git-ignored. Do not remove that, and do not commit `.env.example`
  with real values in it.
- Never paste an API key into an issue, a pull request, a log, or a test.
- Do not commit books, or excerpts longer than a sentence. Test fixtures are
  generated by `tests/fixtures.py`; keep it that way.

If you accidentally commit a key, rotate it first, then tell a maintainer.

## Getting set up

You need Python 3.10+ and Node 18+.

```bash
git clone https://github.com/iamvazghen/bookroom-sdk.git
cd bookroom-sdk

python -m venv .venv && . .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -e "./python[all]"

npm install
npm run build
```

The engine ships inside the package, so there is no second checkout to clone
and no `BOOKROOM_APP_ROOT` to set.

You will need a `GEMINI_API_KEY` to call the real providers. `TYPESAFE_API_KEY`
enables JEv review; without it review is skipped and the run says so. Copy
`.env.example` to `.env` to get started.

## Before you open a pull request

Run the full suite. It costs nothing: the verification scripts use a local mock
provider that speaks the real wire formats, so no credits are spent and no book
is sent anywhere.

```bash
python verify_sdk.py           # 68 checks - in-process behaviour
python verify_facade.py        # 40 checks - the HTTP surface
python verify_examples.py      # 15 checks - the shipped examples and CLI
python verify_equivalence.py path/to/small-book.pdf
python verify_typescript.py    # 53 checks - TS client against the live facade
npm run typecheck && npm test  # 41 tests
```

`verify_clean_install.py` is the slow one — it builds a throwaway virtual
environment and `pip install`s the package. Run it when you change packaging,
`pyproject.toml`, or the engine bootstrap.

## What a good change looks like

- **A bug fix comes with a test that fails before it.** Say which check you
  added.
- **A behavioural change updates the docs.** The README, the Python README and
  `SKILL.md` are part of the deliverable, not an afterthought.
- **Keep the engine vendored files untouched.** The 19 modules in
  `python/bookroom_sdk/_engine/` are deliberately unmodified copies so an
  upgrade is a file copy rather than a merge. If you must change engine
  behaviour, change the SDK wrapper, and say why in the pull request. See
  [_engine/PROVENANCE.md](python/bookroom_sdk/_engine/PROVENANCE.md).
- **American English spelling** in code comments and documentation.
- **No secrets, no book content, no telemetry.**

## Commit messages

Write them for the person debugging at 2am:

```
fix: reject a job kind that does not match its required fields

_start_job required `path` even for review-report jobs, which only need
`report_path`. Clients had to send a dummy source path to review an
existing report.
```

## Reporting bugs

Open an issue with what you did, what you expected, what happened, and the
output of `room.describe()` — it is safe to paste, because it contains no
secret values. If the report is about quality rather than a crash, say which
categories fell below threshold and include `evaluations.json`.

## Security

Do not open a public issue for a security problem. See
[SECURITY.md](SECURITY.md).
